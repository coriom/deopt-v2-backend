- Batch 2: fixture generation 127.358 s, ingestion 4.756 s. Batch 3: 119.985 s and 1.969 s. Batch 4: 95.469 s and 4.355 s. The first Rust invocation incurred a 487.13 s compile and its test ran 54.88 s. These timings include local Anvil mining and fixture setup; they are **not** continuous ingest throughput measurements. The 4-transaction / 8-fill campaign is a bounded correctness workload, not a sustained production traffic model.
- Against a loopback development backend and the genuine persisted fixture wallets, 256 GET history requests with 8 concurrent clients completed in 4.171 s (61.38 requests/s, p50 119.32 ms, p95 157.54 ms). There were no cross-wallet rows or inferred subaccounts. Backend RSS went from 40.09 to 51.24 MiB (51.24 MiB high-water); process CPU time was 7.2 s. After a second PostgreSQL restart, 64/64 reads passed in 1.546 s (41.4/s, p50 118.96 ms, p95 685.9 ms); RSS rose from 51.22 to 67.15 MiB (67.15 MiB high-water), process CPU 1.75 s. This was a **local development-only profile**. The VPS release profile continues to deny unauthenticated wallet history with HTTP 403, so these timings do not establish public API readiness.
- PostgreSQL was limited to 1.5 GiB/1.5 CPU for the later sample; it showed 34.4 MiB RAM and 0.00% instantaneous CPU at the final idle sample. The local backend development process itself had no container limit. The WSL host exposed 12 CPUs, 9,944 MiB RAM, 3,072 MiB swap and roughly 1.08 TB filesystem capacity; these are **not** the Netcup host characteristics. Database size grew from 7,699,479 bytes pristine to 13,679,639 bytes after migrations and 8 fills (5,980,160 bytes total allocation, mostly schema). The tiny workload does not measure long-term disk growth.

**8 GiB sizing: PROVISIONAL.** Compose limits reserve 2 GiB backend, 1.5 GiB PostgreSQL and 256 MiB Caddy; the measured local process and database fit comfortably in those bounds, but build jobs, indexer load, trace latency, sustained concurrency, backup I/O and VPS kernel overhead were not simulated together. Before private host acceptance, repeat the same receipt/replay and concurrent-read workload on the actual VPS under these limits, measure p95 latency, peak RAM/CPU, disk growth and restart recovery, then expand the workload to the intended operational volume. Do not expose wallet history to run that test.

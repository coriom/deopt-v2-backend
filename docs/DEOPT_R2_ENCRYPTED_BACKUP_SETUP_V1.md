# DeOpt R2 encrypted backup setup v1

Scope: preparation and an operator-run synthetic probe. No DeOpt PostgreSQL service has started, and no database backup or restore is claimed. Cloudflare R2 bucket `deopt-private-backups` is operator-provided; its public access setting is operator-reported, not independently inspected here. The S3 endpoint is `https://77dc4e907cd36ee29964c8aff47f7c38.r2.cloudflarestorage.com`.

## One operator intervention, in two terminals

1. In the operator's own WSL terminal, run `bash deploy/vps/operator-deopt-backup-key-wsl.sh --create /mnt/<drive>/<private-backup-directory>/deopt-recovery.gpg`. Select a path on the Windows drive that does not exist. Follow GPG's interactive passphrase prompts. Keep both the encrypted secret-key export and its independent recovery passphrase off the VPS; record the reported full fingerprint in the operator's custody. Test restoring the export in the temporary GPG home, as the script does. Do not paste keys or passphrases into chat or logs.
2. Stage only the public key with `scp -o StrictHostKeyChecking=yes -o ForwardAgent=no "$HOME/.local/share/deopt-backup-gpg/deopt-backup-public.asc" deopt-vps:deopt-bootstrap.stage/deopt-backup-public.asc`. Compare the full fingerprint shown by the WSL script against the fingerprint expected for the VPS root script. Do not copy the secret key to the VPS.
3. The reviewed root-owned copy of `operator-setup-deopt-r2-vps.sh` must be checked against its published SHA-256 before execution. Run it once through the operator's interactive `sudo` session, passing only the public fingerprint as an argument. It installs Debian's rclone package only if absent; leaves Docker, Coolify and GHCR untouched; creates `/root/.config/deopt/rclone.conf` mode 0600; imports only the public GPG key; prompts for the bucket-scoped R2 Access Key ID and Secret Access Key with hidden input; encrypts a synthetic file; uploads and downloads only ciphertext; checks its SHA-256; and checks that invalid credentials fail. The unauthenticated S3 endpoint result is reported separately and never accepted as proof of the bucket's public settings. The script prints only statuses, a temporary ciphertext staging directory, and nonsecret hashes. Do not use shell tracing. A rerun reuses the existing root-only config without reprinting or replacing credentials.
4. In WSL, run `bash deploy/vps/operator-deopt-backup-key-wsl.sh --verify-probe probe.XXXXXXXX <PLAINTEXT_SHA256>` using the probe directory and hash returned by the VPS script. It retrieves the ciphertext through strict SSH, decrypts with the WSL-held private key, and compares the original plaintext SHA-256. This establishes synthetic off-host recovery, not PostgreSQL restoration. The operator should retain the sanitized PASS lines and hashes; do not send keys or config files.

## Recovery after S3 HTTP 400

An unauthenticated request to the S3 API endpoint returned HTTP 400 / `InvalidArgument` after the first operator-run ciphertext upload/download. This is **inconclusive** about public bucket exposure. Cloudflare publishes R2 buckets through either the managed `r2.dev` URL or a Custom Domain; these controls are independent of the S3 API response. See [Cloudflare public-bucket documentation](https://developers.cloudflare.com/r2/buckets/public-buckets/).

The corrected probe classifies HTTP 400 as `S3_ANONYMOUS_CHECK=INCONCLUSIVE_HTTP_400`. HTTP 2xx causes a hard stop. After inspecting **R2 > deopt-private-backups > Settings**, the operator must confirm that **Public Development URL is disabled** and **no Custom Domain has Access to Bucket allowed**. The script then requests the exact acknowledgement `PRIVATE deopt-private-backups` in the interactive VPS terminal. This records `CLOUDFLARE_PUBLIC_ACCESS=OPERATOR_ATTESTED_NOT_API_VERIFIED`; it does not claim an independent API verification. If those dashboard conditions do not hold, stop instead of entering the acknowledgement.

The rerun preserves the root-only rclone config and imported public key. It creates a new synthetic encrypted probe and produces fresh `PROBE_STAGE` and `PLAINTEXT_SHA256`; use `--verify-probe` on WSL as in step 4. No new GPG key or R2 token is needed. An earlier successful upload/download reported by the operator is historical; only the completed rerun and WSL decryption can close this synthetic recovery test.

# DeOpt — préparation de la première release privée Coolify

État vérifié le 2026-11-01 UTC. Cette préparation ne déploie aucun service DeOpt. Le frontend reste sur Vercel.

## Infra et exposition

- Connexion SSH stricte par clé à `deoptops@deopt-vps` : PASS. `ssh` et `docker` sont actifs ; Engine 29.9.2 et Compose 5.6.1. `deoptops` ne peut pas lire le socket Docker, ce qui évite de lui donner implicitement les privilèges root. La politique root effective n'a pas été relue sous sudo dans ce jalon ; le durcissement est rapporté par l'opérateur.
- `ss -lnt` : `8000`, `6001`, `6002` uniquement sur `127.0.0.1`, sans listener IPv6. Depuis WSL, ces trois ports ne répondent pas sur l'IPv4 publique ; `127.0.0.1:8000` sur le VPS répond par une redirection 302. Le compte propriétaire, sa 2FA et le serveur `localhost` Ready sont rapportés par l'opérateur, non vérifiés par une session Coolify de cet agent.
- `80/443` écoutent sur IPv4 et IPv6 et répondent respectivement 503/404 depuis WSL. **8080 écoute aussi sur `0.0.0.0` et `[::]`**. La sortie `sudo docker ps --format '{{.Names}} {{.Ports}}'` fournie depuis la console root Netcup attribue ces trois ports à `coolify-proxy`. Les seuls autres conteneurs indiqués sont `coolify-proxy-error-pages`, `coolify-sentinel`, `coolify`, `coolify-db` et `coolify-redis` ; aucun DeOpt n'y figure. Depuis WSL, une connexion HTTP **et** HTTPS vers l'IPv4 publique port 8080 échoue avant réponse ; depuis le VPS, HTTP sur `127.0.0.1:8080` est réinitialisé et HTTPS ferme la connexion. Le contrôle opérateur filtré de `docker inspect coolify-proxy` donne `API_INSECURE=False`, `API_DASHBOARD=True`, `ENTRYPOINT_8080=False`. La publication 8080 semble donc inutile pour la configuration courante du proxy, mais son retrait nécessite une revue de la configuration Coolify enregistrée, des autres applications et d'un retour arrière. L'échec de nos sondes ne prouve pas l'inaccessibilité depuis tout réseau. [Coolify documente](https://coolify.io/docs/core/networking/proxy/traefik/dashboard) le rôle du mode Traefik insecure et de 8080. Ne pas arrêter ou modifier le proxy dans ce jalon.
- RAM : 7 947 Mio total, 6 571 Mio disponibles ; racine : 157 Gio, 146 Gio libres ; swap absent. Ce sont des mesures au repos, pas une validation de capacité du backend.

## Sauvegarde et reprise

L'opérateur a confirmé depuis `Settings > Backup` : sauvegarde d'instance **activée**, fréquence `0 0 * * *` en UTC, timeout 3600 s, backup avant mise à jour activé ; dernière exécution `Success` le 2026-11-01 à 14:12:58 UTC, base `coolify`, taille 382.14 KB, disponibilité locale. Le `.dmp` a été téléchargé sur Windows et `APP_KEY` est conservée séparément. Ne pas redemander ces données et ne jamais les insérer dans un ticket ou un rapport. La configuration quotidienne est prouvée, **pas encore une deuxième exécution automatique** ni une restauration. [Coolify indique](https://coolify.io/docs/core/backup-and-recovery/instance-backup) qu'une sauvegarde d'instance couvre sa base de contrôle, sans les données applicatives ni les volumes. La future base PostgreSQL DeOpt exige une sauvegarde et une restauration séparées.

Pour une reprise sur un autre hôte, garder également, sous garde chiffrée indépendante, la clé SSH technique Coolify sous `/data/coolify/ssh/keys/`, les entrées `authorized_keys` nécessaires, l'override de ports privés, la version Coolify et la configuration réseau. [La procédure officielle de restauration](https://coolify.io/docs/core/backup-and-recovery/instance-restore) remplace la base Coolify : la tester uniquement sur une cible jetable isolée, avec une copie du `.dmp` et de la clé détenues par l'opérateur. Aucun test de restauration de l'instance active n'est autorisé ici. Le premier backup téléchargé ne prouve ni la cadence quotidienne, ni une restauration réussie.

`deploy/vps/backup-offsite.sh` et les essais PostgreSQL jetables antérieurs sont réutilisables, mais aucune destination hors serveur, garde de clé GPG, rétention, alerte ou restauration de la future base DeOpt n'est validée. Ne pas déclarer la sauvegarde DeOpt prête avant un vrai upload chiffré et une restauration jetable. Ne pas confondre cette base avec `coolify-db`.

## Profil DeOpt et image

`compose.coolify-readonly.yml` reste la source. Il n'a ni Caddy, ni port hôte publié ; PostgreSQL est sur un réseau interne avec volume dédié. Le backend est UID 1001, root FS read-only, capacités retirées, `/ready` en healthcheck, chaîne 84532, indexer, trading, broadcaster et workers désactivés. La route d'historique wallet sans authentification reste HTTP 403 ; CORS n'est pas une preuve d'identité.

Coolify peut transformer la définition Compose lors de la création d'une ressource. Son [Compose déployable](https://coolify.io/docs/services/how-services-work) doit être vérifié distinctement de la source. `deploy/vps/check_coolify_private_compose.py` accepte uniquement une sortie JSON de `docker compose config` avec deux services, images par digest, aucun port ni route proxy, réseau PostgreSQL interne, secret fichier, persistance, identité non-root, flag read-only et chaîne 84532. La source normalisée passe ; aucun Compose réellement généré par Coolify pour DeOpt n'existe encore. Une transformation Coolify inattendue doit donc arrêter la release. Ne pas connecter DeOpt au réseau partagé `coolify` ni lui assigner de domaine par défaut. Le proxy Coolify présent sur 80/443 ne constitue pas une autorisation d'exposer DeOpt.

La construction locale `deploy/vps/build-private-image-local.sh --build-local` a réussi depuis le commit source `acb8c02960928910dfcfa579c93dadac30bb9f61` (Dockerfile SHA-256 `0b051d09fa4b1e3ec60e710aa78bb8ae096cd56e4d38a6c7d9ab700420fb029f`). Les deux images de base sont épinglées par digest. Image `linux/amd64`, étiquette OCI `org.opencontainers.image.revision` exacte, identifiant local `sha256:cbf6ff52b1248d66488175b59577a8cb97b62f947b4d4bf6fab5dc968a328d6b`. Un conteneur local jetable sans réseau a confirmé UID 1001, binaire, entrypoint et migrations présents. **Cet identifiant local n'est pas un digest de manifeste de registre** ; aucune image n'a été publiée. Les paquets APT du Dockerfile ne sont pas figés au numéro de version : une reconstruction ultérieure peut différer. Le registre privé et son accès restent à choisir et autoriser avant une release VPS.

## Séquence future, soumise à autorisation de release distincte

1. La publication 8080 semble inutile au vu des flags Traefik vérifiés par l'opérateur. Préparer séparément son retrait dans `Servers > localhost > Proxy > Configuration` après revue des réseaux, routes et autres applications, avec copie de configuration et retour arrière ; vérifier ensuite 80/443 et le tunnel administratif `127.0.0.1:8000`. Ne pas éditer uniquement le fichier Compose sur disque : [Coolify peut l'écraser depuis sa configuration enregistrée](https://coolify.io/docs/core/networking/proxy/traefik/dashboard).
2. Dans Coolify, créer **uniquement** le projet `DeOpt` et l'environnement `staging` ; aucun domaine ni ressource déployée. Pour la release ultérieure, préférer une ressource `Docker Compose Empty` avec définition revue, sans build Git ou auto-déploiement. Les composants DeOpt devront rester séparés des autres applications. [Coolify avertit](https://coolify.io/docs/applications/builds/docker-compose) qu'un port `ports:` contourne le proxy et peut exposer un service directement.
3. Après autorisation du registre privé, publier l'image issue du commit source contrôlé et enregistrer son digest de manifeste. Épingler également PostgreSQL 16 par digest. Préparer sur l'hôte un mot de passe PostgreSQL dans un fichier privé lisible par UID 1001, sans clé de signature ni secret dans Git. Approuver une destination de backup DeOpt hors serveur et éprouver son restore jetable.
4. Saisir la source Compose sans domaine et vérifier le **Compose déployable** de Coolify. Le rendre en JSON dans un emplacement privé et exécuter `python3 deploy/vps/check_coolify_private_compose.py rendered-compose.json`. Ne pas commettre ce JSON s'il contient des chemins ou valeurs sensibles. Aucun PASS sur la seule source ne remplace ce contrôle.
5. Après autorisation explicite de la release privée, déployer une seule fois. Depuis le conteneur, vérifier `/health` 200, `/ready` selon la disponibilité DB, marchés indisponibles explicitement, historique wallet 403 et méthodes de mutation 405. Vérifier volume PostgreSQL, reprise, logs, absence de ports ou routes proxy DeOpt, puis reprendre un backup DeOpt et tester son restore isolé.
6. Pour rollback, conserver le digest d'image précédent et le backup avant migration. Revenir à ce digest uniquement après vérification de compatibilité du schéma ; ne jamais rétrograder automatiquement la base ou arrêter d'autres applications.

## Verdict

Préparation privée : **BLOCKED**. Les éléments locaux sont prêts à être revus ; la publication proxy 8080 est un point de durcissement séparé. Restent requis pour une release : le Compose Coolify réellement généré, un digest de registre privé, les secrets hôte, une sauvegarde/restauration DeOpt et l'autorisation de release. La sauvegarde Coolify quotidienne est configurée et son dernier run a réussi ; la restauration Coolify et la garde hors VPS des clés techniques restent à confirmer. Aucun backend DeOpt, broadcaster ou domaine n'a été déployé.

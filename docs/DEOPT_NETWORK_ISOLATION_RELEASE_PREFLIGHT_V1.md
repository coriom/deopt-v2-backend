# DEOPT_NETWORK_ISOLATION_RELEASE_PREFLIGHT_V1

Date: 2026-11-04 UTC. Scope: read-only inspection of the Netcup production stack and isolated local Docker tests. No production Compose, proxy, database, Vercel, or chain state was changed. No commit or image was published by this preflight.

## Root cause and target

The Coolify 4.5.3 implementation of `connectProxyToNetworks` in [`bootstrap/helpers/proxy.php`](https://raw.githubusercontent.com/coollabsio/coolify/v4.5.3/bootstrap/helpers/proxy.php) attaches the shared proxy to **every** network of each `coolify.managed=true` container, excluding only the standard bridge/host/none/default networks. Raw Compose does not exempt an application's `db` network. An external Docker network, `internal: true`, and `traefik.docker.network` do not remove that membership.

The operator's root-owned inspection (script SHA-256 `fd7bc2f5200697e2359c805443d131afa246b453eac1f4d493d2ae438058b384`) observed `coolify-proxy` on `coolify`, `dxco90jwpdxyennmquv2elyj_db`, and `dxco90jwpdxyennmquv2elyj_web`; backend on `db` and `web`; PostgreSQL on `db` only. PostgreSQL publishes no host port and uses persistent volume `dxco90jwpdxyennmquv2elyj_postgres_data`; backend `/ready` passed. The initial `pg_isready` container probe returned `NOT_REACHABLE_OR_PROBE_FAILED`, which was **inconclusive**. The corrected root-owned network-namespace probe, SHA-256 `0bada3ce6464c975d688a9fd3323dbe6a8f3f70d149249fd78a9eb019f2de21e`, returned **`PROXY_POSTGRES_TCP=REACHABLE`**. This is a direct TCP-connect result from the running proxy's network namespace to PostgreSQL, with no database credentials.

The committed inspector source has a further fail-closed parsing guard: a failed `nsenter`/Python probe cannot be misread as a TCP refusal. Its source SHA-256 is `a770b770abb6638976246179b91f2e7811022781955e95b6d056ab2256821f9b`; the production `REACHABLE` observation above used the independently hashed earlier version. No follow-up production probe was needed to conclude that the current network is exposed to the proxy.

The candidate [`compose.coolify-socket-readonly.yml`](../compose.coolify-socket-readonly.yml) gives PostgreSQL `network_mode: none` and `listen_addresses=`. PostgreSQL and backend share only a named Unix-socket volume; backend alone joins `web`, where Coolify can connect its proxy. The backend has no `db` network. This preserves the existing `postgres_data` volume key **provided Coolify retains the same Compose project ID**. The candidate requires a newly built image with the reviewed socket-aware entrypoint and a new immutable GHCR digest. The currently deployed image must not be used with this candidate. The legacy Compose is unchanged.

The socket URL uses SQLx's supported URL-encoded host form `%2Fvar%2Frun%2Fpostgresql`; the query-parameter form `?host=/var/run/postgresql` failed with `empty host` in the deployed binary. The entrypoint refuses a missing socket, wrong chain, missing password file, or unset read-only release. `DEOPT_SOCKET_BACKEND_IMAGE` is required; no production digest has been invented. The candidate still needs a check of the production `pg_hba.conf` local authentication method and database role permissions before public wallet access is enabled. No production auth method was changed in this milestone.

## Isolated executable evidence

- `python3 -m unittest deploy.vps.test_coolify_private_compose`: **18/18 PASS**, including cases rejecting PostgreSQL TCP/network exposure, missing socket mount or group, and disabled socket mode. `sh -n deploy/vps/backend-entrypoint.sh` and `git diff --check` passed.
- `cargo test --offline --lib wallet_read -- --test-threads=2`: **2/2 PASS** (1,883 filtered). The wider `cargo test --offline wallet_read` run was stopped during unrelated integration-binary compilation under host load; it is not counted as a passing test campaign.
- `docker compose config --format json` on the candidate with nonsecret production-style variables, then `python3 deploy/vps/check_coolify_private_compose.py --socket-mode`: **PASS**. The validator continues to reject the old shared-`db` architecture in socket mode; it was not weakened to accept the live topology.
- On a disposable PostgreSQL 16 stack labeled as Coolify-managed, a synthetic backend UID 1001/group 999 reached PostgreSQL through the Unix socket; a proxy probe on `web` had neither a PostgreSQL TCP address nor a socket mount. A wrong synthetic database password was rejected. `docker compose up --force-recreate` and restart of the synthetic proxy probe preserved the network split. This establishes local Docker behavior, **not** a Coolify production redeploy or shared proxy restart.
- The existing deployed-image binary was tested locally with the encoded socket URL, applied 71 existing migrations, and returned `/ready` HTTP 200. A new `linux/amd64` Docker image was built locally from backend HEAD `db77a1500cfd98ea56284c3cbc2e959ca1119673` plus the uncommitted candidate changes. Its **local** manifest-list hash was `sha256:f8d9a44de100d1cf92be8cf5b433812b80b5dc98cd433734e2f31a2f64fa4895`; this is not a GHCR registry digest. Running this image against the disposable 71-migration database applied migration 0072: `_sqlx_migrations` became `72|72`, `/ready` returned HTTP 200, and both remained after a backend restart. No production migration occurred.
- The synthetic backend containers and disposable PostgreSQL stack/volumes were removed after the tests. No production volume was touched.

The repository-wide strict Clippy/format gates were not rerun in this scoped network preflight; historical diagnostics remain unresolved. The passing local image build and targeted tests must not be described as a full lint or release-quality pass.

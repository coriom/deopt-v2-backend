## Gates avant le premier démarrage

Le compte SSH `deoptops` accède au VPS, mais `sudo -n` et Docker non privilégié sont refusés. L'API Coolify `GET /api/v1/applications` retourne 401 sans session. Un test d'existence sous `/srv/deopt` depuis `deoptops` ne prouve rien : le répertoire est root-only. La ressource production Raw, son UUID et son rendu réel doivent être créés/exportés par l'opérateur dans le tunnel Coolify. Le rendu local du Compose source passe le validateur, mais ne remplace pas celui de Coolify.

Dans **DeOpt/production**, créer une seule *Application Git Docker Compose* depuis le dépôt backend, branche `main`, fichier `/compose.coolify-readonly.yml`, mode `Raw (deploy file as-is)`, *Manual deployments only*, sans domaine. Utiliser les quatre variables non secrètes du manifeste production. L'ancien Service et l'Application staging restent arrêtés. Vérifier que le commit Git chargé contient le même Compose que le commit OCI, que la ressource utilise un projet Compose et un volume propres à production, et que **Connect To Predefined Network** n'ajoute aucun réseau partagé. Exporter le vrai `Preview Generated Compose` vers `/tmp/deopt-coolify-production-generated.yml` en mode 0600, sans secret en ligne, avant Deploy.

Le contrôle exact est `docker compose config --format json` sur ce Preview avec les quatre variables du manifeste, puis `python3 deploy/vps/check_coolify_private_compose.py --release-manifest deploy/vps/coolify-production-release-v1.json <render.json>`. Ce contrôle exige PostgreSQL sur `db` seul (`internal: true`), backend sur `db` et `web`, deux images par digest, secret par fichier production, aucun port ni route proxy, UID 1001, racine read-only, Base Sepolia 84532, trading/indexer/broadcast désactivés. Vérifier séparément l'identifiant de projet Compose et le nom du volume : un rendu de services identique ne prouve pas à lui seul l'isolation de staging. Si le projet ou le volume sont partagés, **ne pas déployer**.

Le secret production est créé par `operator-create-production-secret.sh`, exécuté avec `sudo` par l'opérateur après vérification SHA-256 d'une copie root-owned. Il crée un nouveau mot de passe sans l'afficher, dans `/srv/deopt/production/secrets/postgres_password`. Ce fichier appartient à `root:1001`, mode 0640, sous un répertoire root-only 0700. Cette exception de lecture de groupe est nécessaire au backend UID/GID 1001 : [Docker Compose ne remappe pas `uid/gid/mode` pour un secret provenant d'un fichier](https://docs.docker.com/reference/compose-file/services/). La lecture réelle dans **les deux** conteneurs doit être vérifiée avant de considérer le déploiement accepté. Le script refuse de remplacer un secret existant ; aucune valeur staging n'est copiée.

## Déploiement et postflight, après les gates

L'opérateur clique une seule fois sur **Deploy** dans la nouvelle Application production. Coolify est l'unique autorité de déploiement. Confirmer dans les logs l'utilisation des digests, l'initialisation PostgreSQL 16, la création de `_sqlx_migrations` et 71 migrations du commit OCI, puis le démarrage Rust. `/health` prouve que le processus répond ; `/ready` doit confirmer la base et la configuration. Tester les routes de consultation autorisées, `POST /health` → 405, une route wallet sans authentification → 403, les marchés absents → indisponibles selon leur contrat. Aucun fill, ordre ou marché ne doit être inventé.

Inspecter les conteneurs par label Compose et non par nom deviné : exactement un `postgres` et un `backend` pour le projet production, aucun port hôte, aucun réseau partagé, `postgres` sur le réseau `db` interne seul, backend non-root et read-only, secret lisible sans affichage, volume PG16 distinct de staging, états healthy, CPU/RAM/disque mesurés. Après un redémarrage contrôlé du seul backend, vérifier que `/ready` revient et que le nombre de migrations et le volume PostgreSQL restent identiques. Ne jamais rétrograder automatiquement le schéma ; si l'application échoue, préserver le volume et arrêter le backend jusqu'à correction.

Le script `backup-offsite.sh` produit désormais le nom exact `BACKUP_OBJECT` et son `CIPHERTEXT_SHA256` après un vrai `pg_dump` chiffré, uploadé puis retéléchargé par R2. Sa clé privée GPG reste hors VPS. Pour le restore, copier **le ciphertext seul** vers WSL, vérifier SHA-256, puis utiliser `restore-offsite-drill.sh` avec `DEOPT_BACKUP_LOCAL_CIPHERTEXT` sur une base PostgreSQL locale jetable vide nommée `deopt_*_test`. Comparer séparément `_sqlx_migrations`, tables, comptes, fills et checkpoints à la base active ; le script n'affirme jamais cette comparaison à lui seul. Aucune planification ni rétention automatique avant le premier restore réel et la revue des alertes.

Le proxy Coolify publie encore 8080 en IPv4/IPv6. Son retrait persistant reste une opération séparée avec rollback ; ne pas redémarrer le proxy pendant cette mise en service privée. L'API HTTPS publique et le raccordement Vercel restent désactivés sans domaine approuvé et contrôle d'accès wallet. Le frontend utilise `NEXT_PUBLIC_TRADING_API_BASE_URL` pour son client de trading et `NEXT_PUBLIC_BACKEND_URL` pour l'admin ; la prochaine étape devra examiner le client exact avant tout changement de variable production. Un backend en lecture seule ne lève ni le message d'indisponibilité du trading ni les restrictions on-chain.
